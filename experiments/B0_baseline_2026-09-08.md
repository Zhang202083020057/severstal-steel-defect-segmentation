## 数据审计与不平衡说明

数据审计以官方 `train.csv` 和 `train_images/` 为准。这里的“正样本数”是某个 `ImageId` 被标为某个 `ClassId` 的有效**图片-类别标注记录数**；同一张图片可含不同类别，因而会有多条记录。它不是图中独立缺陷斑块的数量。

| 类别 | 正样本图片-类别记录数 | 占 12,568 张训练图像的比例 | 缺陷像素占全部训练像素的比例 | 随机 batch=4 不含该类正样本的近似概率 |
|---|---:|---:|---:|---:|
| Class 1 | 897 | 7.14% | 0.0760% | 74.4% |
| Class 2 | 247 | 1.97% | 0.0162% | 92.4% |
| Class 3 | 5,150 | 40.98% | 2.5507% | 12.1% |
| Class 4 | 801 | 6.37% | 0.5349% | 76.8% |

- 训练图像中有任意缺陷的图像为 6,666 张（53.04%），完全无缺陷图像为 5,902 张（46.96%）。训练和测试文件均未发现缺失；测试集为 5,506 张图像。
- Class 2 仅有 247 条正样本记录，而 Class 3 有 5,150 条；按缺陷像素总量计算，Class 3 约为 Class 2 的 157 倍。
- Class 1、2 的正样本掩码平均只占各自原图面积约 1.06% 和 0.82%，缩放 `256×1600` 到 `256×800` 时更容易损失细小缺陷细节。
- 因此，基础 Resize/水平翻转只能产生图像变体，不能改变少数类在随机 batch 中很少出现的事实。后续实验应分别验证类别平衡采样、Focal-Dice、按类别阈值调优和横向切片，避免一次混合多项改动而无法判断收益来源。

类别编号来自比赛官方 `train.csv` 的 `ClassId` 字段。项目中统一使用官方的 `Class 1` 至 `Class 4` 编号，以免把社区常用英文别名误当作额外标注字段。

## 结果解释

平均验证 Dice 为 `0.9063347`。Class 1 和 Class 2 的分数在各 epoch 几乎不变，且分别接近验证集中对应的空掩码比例：

```text
Class 1: (2514 - 179) / 2514 = 0.9288
Class 2: (2514 - 49) / 2514 = 0.9805
```

这说明当前阈值 0.5 下模型很可能没有预测出这两个少数类。总体分数较高，部分原因是竞赛指标规定预测和真实掩码都为空时 Dice=1；因此不能只看平均 Dice，还要关注每一类召回和正样本上的分割质量。详见[Kaggle官方评价说明](https://www.kaggle.com/c/severstal-steel-defect-detection)。

## 推理与提交

完整复现脚本见 [`scripts/run_b0_kaggle.sh`](../scripts/run_b0_kaggle.sh)，它会先训练 B0 模型，再生成 Kaggle Notebook 所需的 `/kaggle/working/submission.csv`。

当前基线测试推理命令：

```bash
python predict.py \
  --data-dir /kaggle/input/competitions/severstal-steel-defect-detection \
  --checkpoint /kaggle/working/outputs/B0_unet_resnet34/best_model.pt \
  --output /kaggle/working/submission.csv \
  --thresholds 0.5,0.5,0.5,0.5 \
  --tta none \
  --submission-format original \
  --batch-size 4 \
  --num-workers 2
```

预期提交文件为 `22,024` 行、两列：`ImageId_ClassId` 和 `EncodedPixels`。
